# การประเมินคุณภาพระบบ RAG (Sai-Mu / เลขศาสตร์)

สคริปต์นี้วัดว่าระบบ RAG "ตอบตรงกับข้อมูลในฐานข้อมูลแค่ไหน" โดยวัด 2 มุม
แยกกัน เพราะเป็นคนละคำถามกัน:

## 1. Retrieval quality — "ค้นเจอข้อมูลที่ถูกต้องไหม"

ก่อน AI จะตอบ ระบบต้องค้นหา chunk ที่เกี่ยวข้องจาก ChromaDB ก่อน (ดู
`retriever_chroma.py`) — ถ้าค้นผิด chunk ตั้งแต่ต้น คำตอบก็ผิดทางแน่นอน
ไม่ว่า AI จะเก่งแค่ไหน วัดด้วย 2 ตัวชี้วัดมาตรฐานที่งานวิจัยด้าน
information retrieval ใช้กัน:

- **Hit Rate@k** — ในคำถามทั้งหมด มีกี่เปอร์เซ็นต์ที่ chunk ที่ถูกต้องอยู่ใน
  k อันดับแรกที่ค้นเจอ (k = จำนวน chunk ที่ระบบดึงมาให้ AI อ่านต่อ)
- **MRR (Mean Reciprocal Rank)** — เฉลี่ยของ 1/อันดับที่เจอ chunk ที่ถูกต้อง
  ยิ่งเจอไวยิ่งได้คะแนนสูง (เจออันดับ 1 = คะแนนเต็ม 1.0, อันดับ 2 = 0.5,
  ไม่เจอเลย = 0) ต่างจาก Hit Rate ตรงที่สนใจ "อันดับ" ด้วย ไม่ใช่แค่เจอหรือไม่

## 2. Faithfulness — "คำตอบมั่วเพิ่มเติมไหม"

ต่อให้ค้นเจอ chunk ถูกต้อง AI ก็อาจสร้างคำตอบที่เกินเลยไปจากข้อมูลที่มีได้
(อาการ hallucination ที่พบได้ทั่วไปใน LLM) จุดนี้วัดด้วยวิธี **LLM-as-judge**
— ใช้ Gemini อีกครั้งเป็นกรรมการเทียบ "คำตอบ" กับ "ข้อมูลอ้างอิงที่ค้นมาได้
จริง" แล้วให้คะแนน 0.0-1.0 ว่าทุกประโยคในคำตอบมีหลักฐานรองรับหรือไม่ (ดู
`judge.py`) วิธีนี้เป็นแนวทางที่ใช้กันแพร่หลายในการประเมิน RAG system
(เช่นเดียวกับ framework อย่าง RAGAS)

**ข้อควรระวัง:** faithfulness score วัดแค่ "ตรงกับข้อมูลอ้างอิงไหม" ไม่ได้
วัดว่า "ข้อมูลอ้างอิงนั้นถูกต้องตามหลักเลขศาสตร์จริงหรือเปล่า" (นั่นเป็นเรื่อง
ของคุณภาพข้อมูลต้นทาง ไม่ใช่เรื่องของ RAG pipeline)

## วิธีรัน

```bash
python -m app.rag.eval.run_eval
```

ตัวเลือกเพิ่มเติม:
```bash
python -m app.rag.eval.run_eval --top-k 6        # ปรับจำนวน chunk ที่ retrieve
python -m app.rag.eval.run_eval --skip-judge      # ข้ามขั้น faithfulness (เร็ว/ประหยัดโควตา — ใช้ตอนแค่อยากดู retrieval)
python -m app.rag.eval.run_eval --reset           # ล้างความคืบหน้าเดิมทิ้งแล้วเริ่มใหม่ทั้งหมด
```

### ⚠️ เรื่องโควตารายวัน (สำคัญมาก)

Gemini free tier มีโควตา **รายวัน** ต่อโมเดลค่อนข้างต่ำ (บางบัญชีแค่ 20
request/วัน/โมเดล) — ต่างจาก rate limit ต่อนาทีที่รอสักพักแล้วลองใหม่ได้
โควตารายวันจะรีเซ็ตแค่วันละครั้งเท่านั้น (เที่ยงคืนตามเขตเวลา Google) รอ/ลอง
ใหม่สักพักไม่ช่วยอะไร ชุดทดสอบ 20 ข้อ + judge อาจชนโควตานี้ได้ง่ายถ้ารันรวด
เดียว

สคริปต์นี้จึงถูกออกแบบมาให้ **บันทึกความคืบหน้าทีละคำถามอัตโนมัติ**
(`results/progress.json`) ถ้าชนโควตากลางทางจะเห็นข้อความแจ้งชัดเจน (ไม่ใช่
error ยาวๆ) พร้อมบอกว่าทำไปแล้วกี่ข้อ — **แค่รันคำสั่งเดิมซ้ำได้เลยหลังโควตา
reset** (รอถึงวันถัดไป) จะข้ามคำถามที่ทำสำเร็จไปแล้วอัตโนมัติ ไม่เสียโควตาซ้ำ
ทำได้แม้จะต้องแบ่งรันข้ามหลายวันกว่าจะครบ 20 ข้อ

เพื่อลดโอกาสชนโควตา ระบบยังแยก**โมเดลของ judge ให้เป็นคนละตัวกับโมเดลที่ตอบ
แชทจริง** (`gemini-2.0-flash-lite` แทน `gemini-2.5-flash`) เพราะโควตารายวัน
นับแยกตามโมเดล — ไม่ไปแย่งโควตาก้อนเดียวกับที่ใช้ตอบคำถามผู้ใช้จริง

**ถ้าอยากรันได้สะดวกไม่ต้องรอข้ามวัน** ทางแก้ถาวรคือเปิด billing ให้โปรเจกต์
Google Cloud (ที่ https://aistudio.google.com — ลิงก์ผูก billing account)
โควตาจะสูงขึ้นทันทีไม่ต้องรออนุมัติ (ยังใช้ free tier ต่อได้ แค่เพดานสูงขึ้น
มาก ไม่ได้บังคับเสียเงินทันที มีโควตาฟรีให้ก่อนถึงจะเริ่มคิดเงิน)

ผลสรุปจะพิมพ์ออกทาง terminal เมื่อรันครบทุกข้อแล้ว และบันทึกรายละเอียดทุกข้อ
(คำถาม, chunk ที่เจอ, คำตอบ, คะแนน) ไว้ที่ `results/eval_<วันที่-เวลา>.json`
— ใช้แนบเป็นหลักฐานในรายงาน/เล่มโปรเจกต์ได้โดยตรง หรือเปิดดูรายข้อว่าข้อไหน
คะแนนต่ำเพื่อไปแก้ข้อมูล/prompt ต่อ

## ชุดคำถามทดสอบ (`test_set.json`)

ตอนนี้มี 20 ข้อ ครอบคลุมทั้งคำถามตรงๆ ("เลข 5 หมายถึงอะไร") และคำถามที่ถาม
อ้อมๆ ("ดาวอังคารตรงกับเลขอะไร") แต่ละข้อระบุ `expected_chunk_id` ไว้ล่วงหน้า
(รู้คำตอบที่ถูกต้องอยู่แล้วจากการดูข้อมูลตรงๆ) — ถ้าอยากเพิ่มชุดทดสอบ เติม
ในรูปแบบเดิม:
```json
{"question": "คำถามใหม่", "expected_chunk_id": "number-XX"}
```

ยิ่งชุดทดสอบครอบคลุมหลากหลายแบบคำถาม (ถามตรง, ถามอ้อม, สะกดผิด, คำถามซ้อน
กันหลายเลข) ยิ่งได้ผลประเมินที่น่าเชื่อถือมากขึ้น

## หมายเหตุการทดสอบ

โค้ดทั้งหมดในนี้ (metric การคำนวณ, การบันทึกผล, การ parse คะแนนจาก judge)
ทดสอบ end-to-end แล้วด้วยการ mock การเรียก Gemini จริง (แซนด์บ็อกซ์ที่พัฒนา
ไม่มีเน็ตออกไป Google API ได้) ยืนยันว่ากลไกทั้งหมดทำงานถูกต้อง — แนะนำให้
รันจริงในเครื่องคุณอีกทีก่อนใช้ผลไปอ้างอิงในรายงาน
